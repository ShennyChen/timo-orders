## 01｜執行摘要與決策地圖

Timo 烘焙坊不是從零開始的品牌：沁沁原本已經接到親朋好友的烘焙訂單，
但缺乏一致的產品排程、訂單記錄、成本與收款管理流程。
本專案的首要目標，是在盡量零固定月費、減少沁沁數位操作負擔的條件下，
把現有生意系統化，再逐步擴大接單。

| 指標 | 說明 |
| :--- | :--- |
| **2 人** | 共同管理訂單 |
| **3 類** | 主要產品入口 |
| **0 月費優先** | 技術選型原則 |

### 已確認的主要方向

- 雙人共用訂單 App：你與沁沁均可新增、修改訂單；沁沁使用簡化大字體介面。
- 訂單資料以 Google Sheets 為核心，App 透過 Google Apps Script 存取。
- 每週產品與節慶禮盒：共用一份 Google 表單，讓顧客自助填寫並進入訂單管理流程。
- 客製化生日蛋糕等：先透過 LINE 討論需求、報價與交期，再由你們手動建立訂單。
- 優先免費工具；不在起步階段導入有固定月費的完整電商平台。

### 重要的進度界線

- **已驗證**：本機 App 能讀取、新增與修改訂單，Google Sheets 的 `Orders` 工作表已出現測試資料。
- **尚未驗證**：公開 HTTPS 前端網址、兩支手機實機同步、Google 表單自動匯入 App、正式營運安全與備份。

## 03｜經營背景、目標與分工

### 經營背景與原則

- 現有客源主要來自親友與熟客；先整理真實銷售資料，不應當成完全沒有客戶的新創。
- 沁沁需兼顧製作與其他工作，且不習慣複雜手機／電腦操作；產品數量與排程必須有彈性。
- 對固定支出高度敏感，優先使用 LINE 官方帳號既有功能、Google 表單／試算表、免費網站工具。
- 先把接單、付款、製作、交付流程穩定下來，再投入流量擴張與更複雜的購物車功能。

### 角色分工

| 角色 | 主要責任 | 共同確認 |
| :--- | :--- | :--- |
| **你**（營運／數位管理） | LINE 客服、表單與試算表、App 維護、訂單整理、付款追蹤、社群與品牌內容 | 交期、報價與特殊訂單可行性 |
| **沁沁**（產品／製作） | 決定可接產品、產能、製作、包裝、品質、交付安排 | 每週菜單、製作負荷、材料與成本 |

**管理原則**：兩人都有新增／修改權限，但首頁應依角色提供不同操作重點，降低沁沁誤觸或負擔。

## 04｜產品與銷售策略

| 產品類別 | 經營方式 | 接單方式／狀態 |
| :--- | :--- | :--- |
| **每週產品** | 每週推出約 1–2 種，方便集中採買與批次製作；曾討論週一至週六收下一週訂單。 | Google 表單自助訂購；**整合尚待實作** |
| **客製化產品** | 生日蛋糕等依需求、口味、尺寸、日期、裝飾與報價討論。 | LINE 洽談 → 確認 → App 手動建單 |
| **節日產品／禮盒** | 如中秋節月餅，依節慶檔期規劃預購與數量上限。 | 與每週產品共用 Google 表單；**整合尚待實作** |

### 既有產品盤點

討論中出現過鳳梨酥、檸檬塔／檸檬派、雪花酥與生日蛋糕等品項。
**這些是示例或測試資料，不代表已核定為正式菜單、售價或長期主力產品。**

- 盤點每種商品的現行售價、材料費、包材費、工時、損耗與配送成本。
- 找出親友最常訂、最好製作、利潤合理且適合批次製作的商品。
- 每週菜單先少量試營運，明確設定截止時間、最大可接量與交付方式。
- 節慶商品另外訂出預購開始／截止日期、可接單量與最後交付日。

## 06｜顧客訂購、付款與履約規範

### 已討論的交付與付款方式

- **交付**：自取及宅配皆列入規劃。
- **付款**：銀行轉帳與線上付款皆曾列為需求；目前未確認線上金流已建置。
- **客製化**：須先確認可行性、價格、交付時間，必要時訂金／尾款分開追蹤。

### 建議標準作業流程（尚待正式定稿）

1. 收到訂單或 LINE 詢問；確認顧客資訊與產品。
2. 確認可接量、製作日期、取貨／宅配資訊與最終報價。
3. 建立唯一訂單編號，標記訂單來源與品類。
4. 提供付款資訊，確認是否已付款／付訂金。
5. 排入沁沁製作清單，於製作完成後更新狀態。
6. 確認已交付，完成對帳、成本與營收紀錄。

## 08｜資料整合：Google 表單與 App

### 已確定的整合需求

- 「每週產品」與「節日產品／禮盒」共用一份 Google 表單。
- 顧客可在表單中選擇商品、禮盒、數量及交付資訊。
- 提交後資料進入 Google 試算表，並能從 App 訂單清單看到，避免二次登記。
- 客製化訂單則由 LINE 討論後手動輸入 App。

### 尚待確認的資料設計

| 待決問題 | 建議處理 |
| :--- | :--- |
| 一張表單能否同時購買多種商品？ | 決定一筆訂單對應單品，或採訂單主檔＋明細的資料模型。 |
| Google 表單如何轉為 `Orders`？ | 設計表單回應轉換流程，避免直接覆蓋 App 現有欄位。 |
| 如何防止重複匯入？ | 增加 `formResponseId`、`source`、`createdAt` 等追蹤欄位及去重邏輯。 |
| 品類如何標示？ | 增加 `category` 區分每週、客製化、節慶。 |
| 付款資訊如何確認？ | 表單送出不等於已付款，需另行對帳及更新狀態。 |

### 三階段營運推進

| 階段 | 工作重點 | 完成標準 |
